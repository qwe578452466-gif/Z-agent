## 独立执行边界

用户在当前会话直接使用 Z-deep-interview，按顺序一问一答。访谈执行不由专家 Agent 承担，不交给主 Agent 编排，不分派 Subagent，不联动其他 Skill。当前会话可以在宿主已提供的能力内阅读资料、解释问题、指导补齐信息和保存产物；无法直接保存 JSON 文件时，直接终止访谈。

Skill/Agent 和工程都是可以访谈的需求对象。后续专家 Agent 读取已确认需求开展设计、实现或审查；它们自身的需求仍需完整访谈，但不构成本项的执行角色。专家三标题 goal、boudaries、SOP(each run) 的要求继续适用于后续专家任务，不成为独立访谈的完成门。

## 提问与缺口处理

不知道答案或有哪些方案是正常起点。先解释为什么讨论这个问题、它依赖哪些条件、不同方向的收益和成本；帮助用户拆解后，再讨论选择。每轮只提出一个问题，模糊问题使用开放式提问。依据充分展开后可以讨论建议，建议与用户决定分开记录。

缺口处理：指出缺口 → 说明影响 → 指导和建议补齐 → 回到原问题。保留缺口与原问题的对应关系；当前会话负责主动发现和引导，没有查明的事实继续标记未知。资料补齐的具体行动按可用能力与现有授权进行。

## 问答记录与恢复

每次提问写入 JSON 待答记录，每次回答保存原文并更新状态；修改答案保留各次回答历史。用稳定问题 ID 关联问题、答案、状态和评估。保存轮次、清晰度、评分依据及实际提供的背景、依赖和取舍；不补造旧轮次未记录的时间或讲解。

参考 OMC 的 QuestionRecord 与访谈状态，原版问题模型含 question_id、session_id、创建/更新时间、状态、问题和 answer/answers；轮次与歧义等位于访谈状态。Z 项目补充显式的逐轮评估与讲解记录，当前采用聚合工作 JSON；实际 Skill 记录器与文件布局尚未实现。

JSON 为中断恢复提供依据。用户在 Round 12 明确了保存方式，尚未指定恢复回顾的呈现方式。Round 14 明确：达到 20 轮仍无法收尾，则继续进入深度访谈。20 是回看进度与关键缺口的检查节点，不是强制停止点。继续围绕未决项解释、拆解与补齐，保留累计轮次、问答历史和每轮评估；不重开 Agent 或其他 Skill 流程。

恢复参照 OMC 的已回答与待答状态：读取 JSON 记录，保留已回答内容，依据最新有效需求接续待答问题。当前需求不额外规定回顾的篇幅或界面形式，呈现细节留到后续设计。

## JSON 保存前提与终止

当前宿主必须能直接保存 JSON 文件。问题记录和每次回答实际保存成功后才能继续；不能保存时直接终止，不联动其他 Agent、Skill 或手工导出方案。写入未成功时不能宣称已经保存。该要求来自 Round 16。

用户明确停止或取消时，参照 OMC 保存已可写入的进度并结束当前访谈；需求未确认时不自动进入下一项。解释后仍无法决定的内容继续作为未决项，通过背景讲解、问题拆解和缺口补齐继续讨论，不默认替用户决定。

## 最新内容与历史保留

全部访谈内容保留，包括原问题、每次回答、实际讲解和当时评估。当前有效需求采用最新访谈内容；同一事项出现新旧差异时，新内容优先，旧内容继续保留作追溯。未被新内容修改的其他事项继续有效，不因新增一轮而丢弃。

既有项目默认按最新访谈内容迭代。当前阶段更新需求文档及受影响结论，标出需要继续讨论的依赖；具体产品设计和实现属于后续阶段。历史事实与当前依据分开，未经查证的工程事实仍保持未知。

## 人类可理解的总结

按示例 → 背景 → 双层总结组织。示例可用伪代码、时序图、表格或其他合适形式，解释已经讨论的内容。第一层用清楚语言说明需求与决定；第二层整理已有技术要求、来源和后续事项。

总结以让人看懂为目标，不增加复述或案例问答等独立理解测试。详细实现、具体设计案例、边界细化和设计验收由后续设计处理。保留已经表达的理由和未知项，不编造用户动机或把未查明事实写成冻结事实。
